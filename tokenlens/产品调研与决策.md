# TokenLens 产品调研与决策

[返回项目介绍](./README.md) · [打开交互原型](./index.html)

## 问题判断

AI 编程工具逐渐成为开发者的日常基础设施，但成本管理仍然是割裂的：

- 不同工具分别计费，用户很难看到统一账目。
- 账单只告诉用户花了多少，不能解释钱具体浪费在哪里。
- 成本追踪和 token 优化由不同工具完成，发现问题后仍要手动寻找和配置方案。

因此，TokenLens 要解决的不是单纯的“记账”或“压缩”，而是连接两者：

> 发现浪费 → 采取行动 → 验证结果

## 目标用户

核心用户是同时使用多种 AI 编程工具的独立开发者、自由职业者和小团队技术负责人。

他们需要比账单更细的成本归因，又不需要企业平台里的权限、审批和多租户系统。产品因此选择纯本地、低配置、个人开发者优先的方向。

## 竞品观察

| 类型 | 代表工具 | 提供的价值 | 留下的空白 |
| --- | --- | --- | --- |
| 命令输出过滤 | rtk | 压缩送入模型的终端输出 | 不追踪整体成本，也不解释优化效果 |
| 上下文压缩 | headroom | 减少过长上下文 | 配置和效果对普通用户不够直观 |
| 成本追踪 | CodeBurn、ccusage | 汇总 token 与花费 | 发现问题后不能直接完成优化 |
| AI 网关与可观测平台 | LiteLLM、Langfuse | 团队级追踪、路由和治理 | 对个人开发者过重 |

这些产品已经分别验证了“看见成本”和“减少消耗”的需求，但两类体验之间仍有断层。

## 机会定义

TokenLens 的定位是个人开发者的 AI 成本副驾：

- 用统一视图回答“钱花在哪里”。
- 用浪费分析回答“为什么会花这么多”。
- 用优化编排回答“现在可以做什么”。
- 用前后对比回答“到底省了多少”。

差异不在于发明新的优化算法，而在于把现有能力组织成一条可以理解和操作的路径。

## MVP 取舍

### 保留

1. **成本总览**：展示总花费、有用与浪费的比例，以及正在消耗成本的会话。
2. **会话分析**：按 Agent 和模型筛选，定位单次任务的 token 构成与浪费原因。
3. **优化编排**：针对命令输出、上下文和模型选型推荐对应动作。
4. **预算守卫**：设置预算、预测月末花费，并在超支前给出干预建议。

### 暂不处理

- 团队权限、审批和多租户管理
- API 网关与模型代理
- 自研 token 压缩算法
- 完整的计费和商业化系统
- 替代现有 AI 编程工具

这些能力会扩大系统范围，却不会帮助当前原型更清楚地验证核心闭环。

## 关键设计决策

### Agent 和模型分开呈现

Claude Code、Cursor、Codex 是用户操作的工具，Sonnet、GPT 等模型才是实际计费对象。将两者拆开，才能准确回答“在哪个工具中，通过哪个模型产生了成本”。

### 用“有用 / 浪费”表示成本

单独展示 token 数量无法帮助用户行动。把每笔成本拆成有用部分与浪费部分，可以让异常更容易被识别，并自然连接到优化建议。

### 编排现有工具

TokenLens 不重新实现 rtk 或 headroom，而是根据浪费类型推荐、配置并验证这些工具。产品价值集中在判断和闭环，而不是底层算法。

### 优化后立即反馈

开启优化动作后，界面同步更新花费、浪费比例和预算预测。这让建议不再停留在说明文字上，也构成产品最重要的正反馈。

## 风险

| 风险 | 应对方向 |
| --- | --- |
| 不同工具的日志格式持续变化 | 将解析能力与产品分析层分离，独立维护适配器 |
| “有用 / 浪费”的判断可能不准确 | 展示判断依据，并允许用户检查具体会话 |
| 现有追踪工具继续增加优化功能 | 聚焦跨工具编排、可视化反馈和个人使用体验 |
| 用户担心代码和会话泄露 | 坚持本地处理，默认不上传原始日志 |

## 验证目标

当前交互原型主要验证三个问题：

1. 用户能否在第一屏理解成本中哪部分是浪费。
2. 用户能否从异常花费定位到具体会话和原因。
3. 优化动作与结果联动后，是否比单独的仪表盘更有价值。

原型不是已上线产品，其中的金额和会话均为演示数据。
